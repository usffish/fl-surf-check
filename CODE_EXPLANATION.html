Code Explanation — fl-surf-check

This document explains the whole program in plain language. No prior programming knowledge is assumed, and no surfing knowledge either.

It is organised as the path of a single run rather than file-by-file, because that is the order things actually happen and the order you would follow when debugging. Line references are to the files as of writing.

What Problem Are We Solving?

Checking the surf forecast is easy. Deciding whether to go is the hard part.

A 9/10 day three hours away and a 5/10 day fifteen minutes away are genuinely hard to compare, because they are measured in different units — one is wave quality, the other is time in a car. Most surf forecasts give you the first number and leave the second entirely to you.

This tool answers the combined question: is it worth the drive? It produces one signed number per spot. Positive means go. The size of the number is your margin.

The One Calculation That Matters

Everything else in the codebase exists to feed this line:

value = sigma(surf) + itch - novelty - drive_minutes / minutes_per_sd

Every term is in the same unit — sigma, standard deviations of surf quality — so they can be added and subtracted meaningfully. minutes_per_sd (default 120) is the exchange rate that converts driving time into that unit.

termmeanstypical range
sigma(surf)how good this is versus Florida's historical record−3 to +3
itchhow long since you last surfed0 to +2
noveltyhow often you have surfed this spot0 to +1.5
drive_minutes / 120the cost of getting there0 to +4

If you remember one thing: one standard deviation of surf is worth two hours of driving. Two sigma is worth four hours. That is the whole philosophy.

What is "Sigma"?

A standard deviation is a measure of how unusual something is compared to normal. Sigma of 0 means "exactly average." Sigma of +1 means "better than about 84% of days." Sigma of +2 is roughly the top 2%.

The tool computes this against the actual historical record of Florida surf — every day since October 2021 — rather than against an opinion of what "good" means. That is why a 2.8 ft day can be genuinely exceptional here and unremarkable in Hawaii; the yardstick is local.

Why sigma and not a 0–10 score

The program also computes a 0–10 SURF score, and shows it, but does not rank on it. A 0–10 score has no natural zero — is 5.6/10 worth driving to? You cannot tell without also knowing how far away it is and what "5.6" implies.

Sigma has a natural zero (average) and, crucially, it can be traded against drive time because both end up in the same unit. That conversion is impossible with an arbitrary 0–10 scale.

Three Numbers That Describe a Wave

Only three inputs really matter, and the code weights them accordingly (scoring.py:56):

Height (35%) — how big. The obvious one, and not the most important.

Period (30%) — the seconds between waves. This is the quality signal. Short period (under 6s) means local wind chop: disorganised slop. Long period (12s+) means the swell travelled a long way from a distant storm, arriving organised and powerful. Period is why a 1 ft day at 11 seconds can be better than a 2 ft day at 5 seconds.

Wind (25%) — direction and speed. Wind blowing offshore (from the land out to sea) holds the wave face up and grooms it. Wind blowing onshore pushes the wave over early and turns the surface to chop. Same swell, completely different session.

The remaining 10% is swell direction — how squarely the swell hits the beach.

How the Code is Organised

fl_surf_check/
├── spots.py        41 Florida surf spots: coordinates, which way the beach
│                   faces, nearest tide station
├── location.py     your zip code -> latitude/longitude
├── distance.py     how far and how long the drive is (real road routing)
├── conditions.py   fetches the forecast: waves, wind, storms, tides
├── climatology.py  builds "what is normal for Florida" from ~6 years of history
├── surflog.py      your personal session log (the only thing stored about you)
├── scoring.py      all the maths. Pure functions, no network, no files.
└── cli.py         ties it together and prints the table

scoring.py does no input or output at all — no network calls, no file reads. That is deliberate: it makes every calculation testable without touching the internet, which is why the whole test suite runs offline in under four seconds.

Step 1 — You type a command

python -m fl_surf_check --zip 33613 --days 5

__main__.py hands straight to cli.py:main() (line 541).

Before anything else, main() checks whether you passed –surfed. If you did, it records a surf session and exits immediately — that path needs no zip code and no internet, so it must run before any network work.

Step 2 — Where are you? (location.py)

geocode_zip() (line 78) turns "33613" into latitude 28.077, longitude −82.445.

It uses pgeocode, an offline database, so after a one-time download this needs no internet. If the zip is not found it falls back to Nominatim (OpenStreetMap's geocoder) over the network, and raises GeocodeError if that fails too.

Step 3 — What is the surf doing? (conditions.py)

One request, not forty-one

fetch_marine_and_wind() (line 151) gets the forecast for all 41 spots in two API calls, not 82. Open-Meteo accepts a comma-separated list of coordinates, so one request covers every spot.

It fetches:

  • From the marine API — wave height, period, direction, and separately the swell partition (see below)
  • From the weather API — wind speed and direction, weather code, CAPE, and precipitation probability (the last three are for thunderstorm detection)

Two wave measurements, used for different jobs

The marine API reports two different things, and the distinction matters:

  • Total sea state — everything in the water, including local wind chop
  • Swell partition — just the organised groundswell, chop removed

The 0–10 SURF score reads the total. Rarity and the historical baseline read the swell, because chop is not rideable and would inflate the numbers.

This was validated against the National Weather Service forecast: NWS said "east 1 foot at 9 seconds"; Open-Meteo's swell read 1.12 ft at 7.9 s, while the total read 1.31 ft at 7.25 s with 0.66 ft of 1.7 s sea-breeze chop mixed in.

It returns a window, not a moment

The function returns a list of hourly readings, not a single reading. This is not incidental — see "Why the best hour, not the current hour" below.

Rate limits are not retried

_with_retry() deliberately does not retry when Open-Meteo says you are rate-limited. Its limit is per-minute, so a sub-second backoff can never outlast it, and each extra attempt spends more of the quota you have already run out of. It fails fast with an accurate message instead.

Step 4 — How far is it? (distance.py)

get_drive_estimate() (line 49) asks the OSRM public routing server for real driving distance and time — actual roads, not straight lines. A 41-spot run is 41 routes, done in parallel, and takes about a second.

If OSRM is unreachable it falls back to straight-line distance × 1.25 (roads are never straight) at an assumed 50 mph, and the result is flagged so the CLI can print ~ beside it. Degrading is better than crashing.

Step 5 — What is normal for Florida? (climatology.py)

This is the piece that makes "unusually good" mean something.

What it builds

build_baseline() (line 255) downloads every day of marine history since 1 October 2021 for all 41 spots in one batched request, and reduces it to a single distribution:

FL normal 1.5ft/7s, good 3.5ft/9s (1787d over 6yr, 41 spots)

Today's swell is then located in that distribution — the VS NORM column.

Four decisions worth understanding

Daily maxima, not hourly samples. A three-day swell contributes 72 highly correlated hours. Treating those as 72 independent observations would badly overstate how much evidence you have. Each day is reduced to its best hour first.

Night is excluded. You cannot surf in the dark, so 3am swell must not set "normal" or supply a day's maximum. The cutoff uses real solar geometry (is_daylight(), line 237), not fixed clock hours, because Florida's daylight swings about three hours between solstices. It is validated against published sunrise/sunset times to within 8 minutes.

The threshold is civil twilight (−6°), not true sunrise — first light is when Florida's wind is calmest and most offshore, so a 0° cutoff would discard the best hour of many days.

One statewide baseline, not one per spot. Grading each break on its own curve would flatter the weak ones — a mediocre Pensacola day would read "p90" beside a genuinely excellent Sebastian Inlet day, because each is only compared to itself. Since the whole point is choosing where to drive, they need one shared yardstick.

Not seasonal. An earlier version windowed the baseline to ±14 days around today. That was removed: it now pools every day regardless of time of year. The tradeoff is real — winter nor'easters pull the distribution up, so a typical August day now reads as somewhat below normal — but "normal" stops shifting meaning with the calendar.

Why it is cached for 30 days

The history request is millions of samples. Running it every invocation trips Open-Meteo's per-minute rate limit, which then starves the live conditions request in the same run, silently dropping every spot to its no-data floor. The cache (.fl_surf_climatology.json) is what prevents that.

Step 6 — Score every hour (scoring.py)

The 0–10 score

score_conditions() (line 247) combines four sub-scores using the weights above. Each is a piecewise-linear curve with explicit control points (HEIGHT_CURVE line 88, PERIOD_CURVE line 102, WIND_PENALTY_CURVE line 114), so they are easy to read and easy to tune.

The height curve is tuned for Florida: it peaks at 5 ft and eases back above 7 ft, where Florida's sandbars close out rather than improve. These three curves are the only region-specific part of the scoring.

Rarity: log-space sigma

rarity_score() compares today's swell to the baseline. The comparison is done in log space — meaning the logarithm is taken before computing mean and standard deviation.

This is not decoration. Raw swell height is heavily right-skewed (skew 1.96): mostly small days with a long thin tail of hurricanes. Applied to that, a plain standard deviation misbehaves badly:

raw feetlog space
skew1.96−0.12
z = 0 lands atp62p50
+1 SDp89p83.5
biggest day on recordz +9.7z +3.4

Two concrete failures on the left: "zero standard deviations from average" lands at the 62nd percentile — the mean is not the middle. And the biggest day ever becomes +9.7 sigma, which at 120 min/sigma would justify a nineteen-hour drive.

The intuition: logs turn multiplication into addition, so log space measures ratios rather than differences. The gap between 1 ft and 2 ft is a doubling and feels enormous; between 11 ft and 12 ft it is marginal. Raw arithmetic calls both "one foot."

Why the best hour, not the current hour

pick_best_hour() scores every surfable hour in the forecast window and reports the best, rather than whatever hour you happened to run the command.

Two reasons. First, the comparison would otherwise be unfair: the baseline is built from each day's best hour, so scoring it against an arbitrary current hour is apples-to-oranges. Measured, a randomly chosen hour scored a median of p34 against that baseline when it should average p50 — a systematic 16-point understatement.

Second, and more usefully, Florida's wind swings hard through the day. Measured at Cocoa Beach over July–August, the sea breeze rotates from 232° at 05:00 (offshore) to 125° by 15:00 (onshore), roughly doubling in speed. Same swell, very different surf. So the honest answer is often "not now, but tomorrow at 11" — which is what the BEST column tells you.

Thunderstorms are a gate, not a penalty

Rain does not stop anyone surfing. Lightning does — and a surfer is the tallest conductive object on a flat wet plain.

So storm risk is deliberately not folded into the 0–10 score. A perfect 8 ft swell under a squall line is not "slightly worse surf," it is surf you must not paddle out into. storm_risk() reports it separately, it forfeits any drive allowance, and an active storm overrides the verdict entirely.

Risk requires both instability (CAPE) and precipitation probability: high CAPE on a dry day is a loaded gun with no trigger, and heavy rain with no instability is just rain.

Step 7 — Your surf log (surflog.py)

The only thing the program stores about you. Everything else it caches describes Florida and is identical for every user.

python -m fl_surf_check --surfed "apollo"              # today
python -m fl_surf_check --surfed "ponce" --on 2026-08-18

Stored as JSON at ~/.fl_surf_log.json — outside the repository, and gitignored regardless. It is a record of where you go and when, which does not belong in a public repo. Writes are atomic (temp file, then rename) so an interrupted write cannot truncate your history.

Spot names are fuzzy-matched, so apollo finds Apollo Beach (Canaveral NS). But an unrecognised name is refused, not guessed — a wrong guess silently logs a session against the wrong break and quietly skews everything downstream.

Itch — days since you last surfed

itch = days_since_last × 0.05

Linear and uncapped. A week out of the water is worth about 42 minutes of extra driving; a month about three hours.

It never changes the ranking. It is identical for every spot, so it slides the whole board and moves the go/no-go line without reordering anything — which is exactly "make me more willing to drive," as distinct from "send me somewhere different."

An empty log means zero itch, not infinite. A fresh install should not open by demanding you drive across the state.

Novelty — how often you have surfed each spot

A z-score of visit counts across all 41 spots, so spots you keep returning to get handicapped and neglected ones surface. This one does reorder.

Two corrections to a plain z-score, both for measured reasons:

Log-transform first. Visit counts are severely zero-inflated — most spots at zero, a few high. On a realistic 200-session log, raw counts penalise the most-surfed spot 1.7× harder than log space does, and a home break's penalty runs away without bound.

Shrink by evidence — n / (n + 20). Even in log space, a young log produces huge z values simply because almost everything is zero: a single logged session has a raw z of +6.3, which at 120 min/sigma is a twelve-hour handicap from one surf.

Worth knowing which correction does what, because it is counterintuitive: the log transform does nothing for the single-session case — log and raw give an identical z there. It is the shrinkage that rescues that. The log earns its place on mature lopsided logs.

Why Things Are Shaped Oddly

This section exists because several parts of this code look over-engineered until you know what they are defending against. Each of these was a real bug.

Distance is not z-scored. It would be natural to standardise drive time the same way swell is. It breaks the calibration: measured against the shipped spot list, a distance z of −1.0 is 30 miles from Daytona but 109 miles from Tampa. If "one sigma closer" means two different drives, it cannot be worth a fixed number of minutes. Raw minutes keep the units absolute.

Sigma is monotonic in height, on purpose. The absolute height curve rolls off above 7 ft, but rarity does not (APPLY_CLOSEOUT_ROLLOFF = False, line 436). So SURF and VALUE will disagree on very large days. That is intentional — the size at which a break stops being fun depends on who is paddling out.

Rarity labels are relative, not fixed percentiles. Shrinkage imposes a ceiling on the attainable percentile. When labels were fixed cutoffs (≥93, ≥97) and the ceiling sat near p91, the top two labels were dead code no input could produce. They are now fractions of the attainable range.

The flat-column guard uses a tolerance, not sd <= 0. When every spot has the same visit count the spread is mathematically zero — but summing N identical floats and dividing leaves the mean off by ~1e-16, so sd lands near zero rather than on it. Dividing by that conjures z = ±1.0 from rounding noise. Platform-dependent: CI failed on a value that the development machine computed as exactly 0.0.

The best-hour ranking uses a tuple key. It reads (1, sigma) for hours with data and (0, surf.total) for those without. A single expression mixing the two — sigma if sigma is not None else surf.total — compares scales that do not match: sigma runs −3 to +3, surf.total runs 0 to 10. A data-free hour scores ~1.8 on the 0–10 scale and beat every real hour. It surfaced the first time a window ran past the end of the marine model (–days 7), and every spot reported "Flat - stay home" on an ordinary forecast.

Tides are keyed by (station, timezone). NOAA returns times in the station's own local time. Comparing those against a naive datetime.now() is only correct when the two happen to match. Florida spans two timezones, and Pensacola once reported the next morning's high tide instead of an imminent low — 13 hours wrong, with the tide state inverted.

Testing

python -m pytest tests/ -q

All tests run offline — network calls are mocked and build_baseline takes an injectable client — so the suite is fast and works in CI.

filecovers
test_scoring.pythe scoring curves: monotonicity, bounds, Florida tuning
test_climatology.pybaselines, rarity, solar geometry, storms, the value score
test_surflog.pythe log, itch, novelty
test_cli_offline.pyend-to-end runs with the network mocked

One habit worth copying

Several tests here were written as regression tests, then verified to fail when the fix was reverted. That matters: one test in this repo was originally written to cover the log transform, passed with the log transform deleted, and had to be re-pointed at what it actually covered (the shrinkage).

A regression test that cannot fail is worse than no test — it is a false reassurance.

Common Questions

Q: Why does it recommend a spot with worse surf than another one?

Because VALUE is not surf quality — it is surf quality minus the drive. A 5.3 twenty-four minutes away routinely beats a 6.2 three hours away. The SURF column is shown precisely so you can see when this is happening.

Q: Why is the top spot's VALUE negative?

Nothing is worth the drive today. That is a real answer, not a failure. Use –worth-only to hide everything negative.

Q: Why does it keep saying "below normal" when the forecast looks fine?

below normal fires at roughly p20 or worse — the bottom fifth of everything Florida has produced since 2021. It is a comment on the swell against history, not on whether the trip makes sense. A spot can be below normal and still rank well because it is close.

Q: The first run took ages. Is it broken?

No. The first run builds the historical baseline (millions of samples) and downloads the zip-code database. Subsequent runs use the cache and take a few seconds.

Q: Why does –days 7 sometimes show fewer usable days than –days 5?

Seven days is the marine model's hard limit, and the window starts at the current hour — so a 168-hour request runs off the end and the tail comes back empty. The tool handles this correctly now, but the far end of a 7-day forecast is genuinely thinner than the near end.

Q: How much should I trust day 5 of the forecast?

Less than day 1. Florida swell decorrelates quickly — the day-over-day correlation of daily-max swell height is 0.74 at one day but 0.26 by four. The tool says so in the output for runs of four days or more. Treat the far end as a plan, not a promise.

Q: I surfed but forgot to log it. Does that matter?

Yes, and nothing can detect it. Novelty will think you have never surfed a spot you go to weekly, and itch will keep climbing as though you have been dry. Both factors are worth exactly as much as your logging discipline. –no-personal turns them off if the log drifts out of date.

Q: Can I use this outside Florida?

Not as-is — the spot list is hardcoded and the scoring curves encode "Florida beach break." The data sources are all global, so the plumbing would work, but the curves would need re-tuning. See "Adding another region later" in the README, which includes measured Pacific Northwest numbers showing the Florida height curve inverting on that coast.

Q: Why is scoring.py the biggest file with no imports beyond math?

Deliberate. It contains every calculation and no input/output, so all of it is testable without a network or a filesystem. That is what lets 161 tests run offline in under four seconds — and it is why numpy was kept out of it even where numpy would have been convenient.
