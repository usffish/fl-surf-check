Code Explanation — fl-surf-check

A walkthrough of the actual code, function by function.

Assumed: you can read basic Python but may not know its idioms, and you are comfortable with statistics (z-scores, skew, Bayesian shrinkage need no introduction). So this explains @dataclass and generator expressions, not what a standard deviation is.

Organised as the path of one run, because that is the order the functions actually execute. Line numbers are as of writing.

The command

python -m fl_surf_check --zip 33613 --days 5

python -m runs a package, which executes __main__.py:

from .cli import main
raise SystemExit(main())

SystemExit sets the shell exit code from whatever main() returns — 0 for success, 2 for a bad argument. That is why every early-return in main() returns a number.

spots.py — the data the whole thing hangs off

@dataclass(frozen=True)
class Spot:
    name: str
    region: str
    lat: float
    lon: float
    facing_deg: float
    tide_station: str
    notes: str = ""
    tz: str = "America/New_York"

@dataclass is a decorator that writes the boilerplate for you — without it you would hand-write __init__, __repr__ and __eq__. frozen=True makes instances immutable: spot.lat = 5 raises an error. That is deliberate, since these are constants.

The fields with = something have defaults, so most spots omit tz, and only the three Panhandle spots pass tz="America/Chicago".

The one computed field

@property
def offshore_deg(self) -> float:
    return (self.facing_deg + 180) % 360

@property makes this callable as spot.offshore_deg — no parentheses — so it reads like an attribute but runs code.

facing_deg is the compass bearing the beach faces. Offshore wind comes from the opposite direction, hence + 180. The % 360 wraps it: a beach facing 270° would give 450°, which % 360 turns back into 90°.

This one line is why wind scoring works for every spot without a second data column.

location.py — zip to coordinates

geocode_zip() (line 78) returns an Origin dataclass holding lat, lon and a label. It tries pgeocode first (an offline database, so no network after the first download), then falls back to Nominatim over HTTP, then raises GeocodeError.

The pattern to notice — it appears everywhere in this codebase:

try:
    ...
except (requests.RequestException, ValueError, KeyError):
    ...

Specific exception types, never a bare except:. A bare except also catches KeyboardInterrupt, so Ctrl-C would be swallowed.

conditions.py — fetching the forecast

Why the return type is a list, not a value

def fetch_marine_and_wind(spots, hours_ahead: int = FORECAST_HOURS):

It returns {spot_name: [(unix_time, Conditions), ...]} — an hourly series per spot, not one reading each. That shape exists because of a measured bias; see pick_best_hour below.

All 41 spots come back in two HTTP requests, not 82, because Open-Meteo accepts comma-separated coordinates:

"latitude":  ",".join(str(s.lat) for s in spots),
"longitude": ",".join(str(s.lon) for s in spots),

(str(s.lat) for s in spots) is a generator expression — it produces values lazily instead of building a list first. ",".join(...) consumes it, giving "30.67,30.28,30.24,...".

Slicing the window out of the response

def _window(hourly, hours_ahead):
    start = hourly.Time()
    interval = hourly.Interval() or 3600
    now = int(dt.datetime.now(dt.timezone.utc).timestamp())
    i0 = max(0, (now - start) // interval)
    n = max(1, hours_ahead * 3600 // interval)
    return int(i0), int(n), int(start + i0 * interval)

The API returns data starting at midnight UTC today, but we want from now onward. i0 is how many hours to skip: seconds elapsed divided by seconds per hour. // is integer division — it discards the remainder rather than giving a float.

hourly.Interval() or 3600 is Python's idiom for "use this, unless it is falsy." If Interval() returns 0 or None, you get 3600. Without it, (now - start) // 0 would crash.

Reading a column, with NaN handling

v = float(values[i])
out.append(None if v != v else v)   # filter NaN

v != v looks like nonsense, but it is the standard NaN test: NaN is the only value not equal to itself, per IEEE-754. The API returns NaN for hours beyond the model's range, and this converts them to Python None, which the rest of the code checks for explicitly.

Rate limits are not retried

except Exception as exc:
    last = exc
    if _is_rate_limit(exc):
        raise
    if i < attempts - 1:
        time.sleep(backoff * (2 ** i))

raise with no argument re-raises the exception currently being handled. The retry loop deliberately gives up immediately on rate limits: Open-Meteo's limit is per-minute, so backoff * 2**i (0.5s, 1s) can never outlast it, and each attempt spends more of a quota already exhausted.

distance.py — real driving time

get_drive_estimate() (line 49) calls the OSRM routing server and returns a DriveEstimate. On any failure it falls back:

except (requests.RequestException, KeyError, IndexError, ValueError, TypeError):
    straight = straight_line_miles(origin_lat, origin_lon, dest_lat, dest_lon)
    approx_miles = straight * ROAD_WINDINESS_FACTOR
    return DriveEstimate(approx_miles, (approx_miles / FALLBACK_AVG_SPEED_MPH) * 60.0,
                         source="estimate")

source is what lets the CLI print ~ beside estimated rows. The tool degrades instead of crashing, and tells you it degraded.

In cli.gather() the 41 routes run concurrently:

with concurrent.futures.ThreadPoolExecutor(max_workers=6) as pool:
    futures = {pool.submit(get_drive_estimate, ...): s for s in spots}
    for fut in concurrent.futures.as_completed(futures):
        drives[futures[fut].name] = fut.result()

pool.submit returns a Future — a placeholder for a result that has not arrived. The dict maps each future back to its spot, so when as_completed yields them in finish order (not submission order) we still know which spot each belongs to. Threads work here because this is I/O-bound: they are waiting on the network, not competing for CPU.

scoring.py — the sub-scores

Curves as data, not if statements

HEIGHT_CURVE = [
    (0.0, 0.0),
    (0.7, 1.0),
    (1.5, 3.5),
    (2.5, 6.5),
    (3.5, 9.0),
    (5.0, 10.0),   # peak - about as good as Florida gets
    (7.0, 8.5),
    (10.0, 6.0),
    (15.0, 3.5),
]

Each tuple is (feet, score). Note it peaks at 5 ft and declines — Florida sandbars close out above roughly 7 ft, so bigger stops being better.

_interpolate() walks these points:

for (x0, y0), (x1, y1) in zip(points, points[1:]):
    if x0 <= x <= x1:
        t = (x - x0) / (x1 - x0)
        return y0 + t * (y1 - y0)

zip(points, points[1:]) pairs each point with the next one — a common Python trick for sliding over consecutive elements. points[1:] is the list from index 1 onward, so you get ((p0,p1), (p1,p2), ...).

Inside the matching segment, t is the fraction of the way across (0 to 1) and the return is the standard linear blend. Interpolating rather than bucketing means 2.49 ft and 2.51 ft score almost identically, instead of falling into different tiers.

Wind: direction weighted by speed

offset = angular_difference(wind_direction_deg, spot_offshore_deg)
alignment = math.cos(math.radians(offset))

angular_difference returns 0–180°. Taking the cosine maps that to +1 for perfectly offshore, 0 for cross-shore, −1 for onshore — a smooth, continuous alignment measure with no special cases.

if wind_speed_mph <= 4.0:
    return 8.5 + 1.5 * max(0.0, alignment)

Under 4 mph it is glassy and direction barely matters, so this short-circuits to a high score. max(0.0, alignment) means onshore wind gets no bonus but no extra penalty either.

influence = min(1.0, (wind_speed_mph - 4.0) / 14.0)
strength_penalty = _interpolate(wind_speed_mph, WIND_PENALTY_CURVE)
score = 6.0 + (alignment * 4.0 * influence) - strength_penalty
return max(0.0, min(10.0, score))

influence ramps direction's importance in from 0 at 4 mph to 1 at 18 mph. strength_penalty grows with speed regardless of direction, so a 30 mph offshore gale still scores badly. max(0.0, min(10.0, score)) is the clamp idiom — squeeze a value into a range without an if.

Combining them

total = (
    WEIGHTS["height"] * h
    + WEIGHTS["period"] * p
    + WEIGHTS["wind"] * w
    + WEIGHTS["swell_direction"] * d
)

A plain weighted sum with WEIGHTS summing to 1.0, so the result stays on 0–10. Then a confidence string records whether any inputs were missing:

if not conditions.has_wave_data:
    confidence = "none"
elif conditions.wind_speed_mph is None:
    confidence = "partial"

This matters because missing wind scores a neutral 5.0, so a data-free spot still produces a plausible-looking number. confidence is how the CLI knows to flag it.

climatology.py — what "normal" means

This module answers: is 2 ft good? You cannot know without the historical distribution.

Reducing hours to days

def _daily_maxima(values, times):
    days = times // 86400
    edges = np.flatnonzero(np.diff(days)) + 1
    groups = np.split(values, edges)
    return (np.array([g.max() for g in groups if len(g)]), ...)

times // 86400 converts unix seconds to a day number (86400 seconds per day). np.diff gives differences between consecutive elements, so it is 0 within a day and 1 at each boundary. np.flatnonzero returns the indices where that is non-zero — the boundaries — and np.split cuts the array there. Each group is one day, and .max() takes its best hour.

Why: a three-day swell contributes ~72 highly correlated hourly readings. Treating those as 72 independent observations would badly overstate the evidence behind any percentile.

Filtering to daylight

finite = ~np.isnan(h) & ~np.isnan(p) & is_daylight(times, spot.lat, spot.lon)

These are element-wise boolean arrays, not single values. ~ is NOT, & is AND, applied to every element at once. The result is a mask, and h[finite] keeps only the positions where it is True. This is NumPy's "vectorised" style — no Python loop, so it runs at C speed over millions of elements.

is_daylight implements the NOAA solar-position formulas to get the sun's elevation, then tests it against −6° (civil twilight). Fixed clock hours would be wrong: Florida daylight shifts about three hours between solstices.

Log-space statistics

pos_h = pooled_h[pooled_h > 0]
log_h = np.log(pos_h) if len(pos_h) else np.array([0.0])

return Baseline(
    ...
    log_height_mean=float(log_h.mean()),
    log_height_sd=float(log_h.std()),
)

The baseline stores mean and SD of the logarithm, not of the raw values. Swell height is strongly right-skewed (measured skew 1.96); in log space it is near-symmetric (−0.12), so the usual z-score assumptions hold.

Then:

def _log_z(value, log_mean, log_sd):
    if value is None or log_sd <= 0.0:
        return None
    if value <= 0.0:
        return -3.0
    return (float(np.log(value)) - log_mean) / log_sd

A standard z-score, computed on log(value). The two guards matter: log_sd <= 0 would divide by zero, and log(0) is undefined — a flat ocean floors at −3 rather than crashing.

Concretely, on the real record the raw-vs-log difference is not subtle:

record 14.5 ft dayz +9.7z +3.4

At the tool's exchange rate, +9.7σ would justify a nineteen-hour drive.

The disk cache

load_baseline() returns the cached JSON if _cache_is_fresh(), else rebuilds and writes it. The write is atomic:

tmp = f"{path}.tmp{os.getpid()}"
with open(tmp, "w") as fh:
    json.dump({...}, fh)
os.replace(tmp, path)

Write to a temp file, then os.replace — which is atomic on POSIX. A crash mid-write leaves the old cache intact rather than a truncated one. os.getpid() in the name prevents two simultaneous runs colliding.

The cache is not an optimisation. The history request is millions of samples; running it every invocation trips the rate limit, which then starves the live forecast request in the same run.

scoring.py — rarity and the value score

Rarity, with a dynamic denominator

numerator = 0.0
denominator = 0.0
if ph is not None:
    numerator += ph * WEIGHTS["height"]
    denominator += WEIGHTS["height"]
if pp is not None:
    numerator += pp * WEIGHTS["period"]
    denominator += WEIGHTS["period"]

if denominator == 0:
    return RarityScore(None, ...)

combined = shrink_percentile(numerator / denominator, baseline.n_days)

The denominator accumulates only the weights actually used. If period is missing, it drops out of both sums rather than being counted as zero — so absent data does not read as bad data. Dividing by the accumulated weight renormalises whatever remains.

Shrinkage

def shrink_percentile(percentile, n_days, prior_days=RARITY_PRIOR_DAYS):
    if n_days <= 0:
        return 50.0
    return (percentile * n_days + 50.0 * prior_days) / (n_days + prior_days)

Laplace's rule of succession, generalised from a proportion to a percentile: mix the observation with prior_days (30) pseudo-observations of "perfectly average." With the current 1,787-day baseline a p98 reading barely moves, to p97. With 8 days behind it, the same reading lands near p60.

The value score

total = sigma + itch - novelty - cost

Every term is in standard deviations of swell, which is what makes them addable. cost converts minutes into that unit:

cost = max(0.0, drive_minutes) / minutes_per_sigma

with minutes_per_sigma = 120, so one sigma of surf buys two hours of driving. max(0.0, ...) guards against a negative duration producing a bonus.

Distance is deliberately not z-scored. Standardising it would make it relative to whichever spots are in the list: measured, a distance z of −1.0 is 30 miles from Daytona but 109 miles from Tampa. "One sigma closer" cannot be worth a fixed number of minutes in both.

Picking the hour

for ts, cond in readings:
    if not is_daylight_fn(ts, spot.lat, spot.lon):
        continue
    surf  = score_conditions(cond, spot)
    rare  = rarity_score(cond, baseline)
    sigma = effective_sigma(rare, surf)

    has_data = sigma is not None
    key = (1, sigma) if has_data else (0, surf.total)

    if best is None or key > best[0]:
        best = (key, entry)

Every surfable hour is scored and the best kept. Two things to notice.

continue skips to the next loop iteration — night hours are not scored at all.

The tuple key. Python compares tuples element by element: it checks the first item, and only looks at the second if the first ties. So (1, anything) always beats (0, anything), and hours with data are compared among themselves by sigma while hours without are compared by surf.total.

The two scales are never compared against each other, and that is the entire point. Written the obvious way —

key = sigma if sigma is not None else surf.total     # BUG

— it compares sigma (−3 to +3) against a 0–10 score. A data-free hour scores about 1.8 on that scale (the neutral wind and direction sub-scores), which beats any realistic sigma. Every spot then reported an empty hour as its best, and the whole table read "Flat - stay home" on an ordinary forecast. It only appeared once a window ran past the end of the marine model, at –days 7.

surflog.py — the personal factors

@dataclass
class SurfLog:
    sessions: list[Session] = field(default_factory=list)
    path: str = DEFAULT_LOG_PATH

field(default_factory=list) rather than = []. A plain [] default would be created once and shared by every instance — the classic Python mutable default bug. default_factory calls list() fresh per instance.

Visit counts include the zeros

def visit_counts(self, spot_names):
    counts = {name: 0 for name in spot_names}
    for s in self.sessions:
        if s.spot in counts:
            counts[s.spot] += 1
    return counts

Every spot starts at 0, so unvisited spots are present in the result. That is required: novelty is a z-score across the whole list, and the zeros are most of the distribution.

Novelty

logged   = [math.log1p(c) for c in counts]
mean     = sum(logged) / len(logged)
variance = sum((x - mean) ** 2 for x in logged) / len(logged)
sd       = math.sqrt(variance)

if sd <= 1e-9 * max(1.0, abs(mean)):
    return {n: 0.0 for n in names}

confidence = total / (total + prior_sessions)
return {n: weight * ((logged[i] - mean) / sd) * confidence
        for i, n in enumerate(names)}

math.log1p(c) is log(1 + c) — needed because log(0) is undefined and most spots have zero visits.

Written in plain Python rather than NumPy on purpose: scoring.py imports only math, so every calculation is testable with no dependencies.

Two corrections to a plain z-score, each fixing a measured failure:

  • The log. Raw counts are severely zero-inflated. On a realistic 200-session log, raw counts penalise the most-visited spot 1.7× harder, and it runs away without bound.
  • confidence. Even in log space a young log gives huge z-scores because almost everything is zero — a single logged session has a raw z of +6.3. Multiplying by n / (n + 20) keeps a three-session log quiet.

Worth knowing which fixes what: the log does nothing for the single-session case (log and raw give an identical z there). The shrinkage rescues that one.

The float-tolerance guard

sd <= 1e-9 max(1.0, abs(mean)) rather than sd <= 0. When every spot has the same count the spread is mathematically zero — but summing 41 identical floats and dividing leaves the mean off by ~1e-16, so sd lands near* zero. Dividing by that produces z = ±1.0 from rounding noise. It is platform-dependent: CI failed on a value the development machine computed as exactly 0.0.

Each row is a plain dict of already-computed objects. render() only formats — it never calculates — so display changes cannot alter a score.

Sorting

if any(r["value"].total is not None for r in out):
    out.sort(key=lambda r: (r["value"].total is not None, r["value"].total),
             reverse=True)
else:
    out.sort(key=lambda r: r["worth"].total, reverse=True)

key= takes a function returning what to sort by. The tuple puts rows with a value first, then orders by the value itself — the same trick as pick_best_hour, and here it also stops None from being compared against a float, which raises TypeError in Python 3.

The else branch is the legacy blend, used only when –no-history means there is no baseline and therefore no sigma.

Testing

python -m pytest tests/ -q     # 161 passed in ~2s

Everything runs offline. Two techniques make that possible.

Dependency injection. build_baseline(spots, client=...) accepts a client object, so tests pass a fake:

class _FakeClient:
    def weather_api(self, url, params=None):
        self.calls += 1
        return [...]

Then assert client.calls == 1 proves all 41 spots were fetched in one batched request, not 41 separate ones.

Monkeypatching. mock.patch.object(cli, "fetch_marine_and_wind", _fake_marine) swaps the real function for a fake for the duration of a test.

One habit worth copying

Several tests here were written, then verified to fail when the fix was reverted. That is not paranoia. One test in this repo was written to cover the log transform, passed with the log transform deleted, and had to be re-pointed at what it actually covered (the shrinkage).

A regression test that cannot fail is worse than no test.

Common Questions

Q: Why does scoring.py import only math when NumPy is already a dependency?

So it has no I/O and no heavy dependencies, which makes every calculation testable in isolation. NumPy was deliberately kept out even where it would have been shorter — the plain-Python mean and variance in novelty_penalties are that trade in action.

Q: What is key > best[0] comparing?

Tuples. Python compares them element-wise, left to right, so (1, -0.5) beats (0, 9.9) — the first element decides and the second is never reached. That is what keeps sigma and the 0–10 score on separate tracks.

Q: Why v != v instead of math.isnan(v)?

Both work. v != v is the classic idiom and needs no import — NaN is the only value that is not equal to itself.

Q: Why do so many functions return None instead of raising?

Because missing data is normal here, not exceptional. An API can omit an hour, a spot can have no baseline, a log can be empty. Returning None lets the caller decide; rarity_score returning None sigma is what makes the tuple key necessary, and the CLI prints - rather than crashing.

Q: Why is Spot frozen but Conditions not?

Spot is a constant. Conditions gets filled in stages — the marine request sets wave fields, the weather request adds wind, the tide request adds tide — so it has to be mutable.

Q: What actually runs when there is no surf log?

itch and novelty are both 0.0, so value = sigma - cost exactly. The personal factors are additive terms that vanish, not a separate code path.

Q: Where would I change how much a good day is worth?

MINUTES_PER_SIGMA in scoring.py (line 612), or –minutes-per-sd per run. Raising it makes the tool more willing to send you on long drives.

Q: Where would I change what counts as good surf?

HEIGHT_CURVE, PERIOD_CURVE and WIND_PENALTY_CURVE (scoring.py, lines 88–120). They are plain lists of (input, score) points — edit the numbers, no logic changes. These three are also the only region-specific part of the scoring, so a different coast needs its own set.
